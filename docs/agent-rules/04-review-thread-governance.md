# 04 专用审查线程治理

## 1. 适用场景

1. 连续多轮修复推进，或单轮改动文件较多时，默认启用专用审查线程。
2. 分工如下：修复线程写代码和验证；审查线程逐文件审查；主线程做裁决与对外口径。

## 2. 审查输入要求

1. 修改文件清单。
2. 验证命令与输出摘要。
3. 本轮目标问题范围。

## 3. 偏航纠正流程

1. 审查线程偏离指定范围时，主线程先纠偏并重派更窄任务。
2. 同一审查线程连续两次偏离，关闭并重建新审查线程。
3. 在逐文件审查完成前，不得用“子线程口头完成”作为通过依据。
4. 当确认修复线程仍在工作时，主线程应保持 `wait_agent` 长等待，不因短超时中断主线收口。

## 4. 标准五步闭环流程

每个目标文件或清晰修复切片必须按以下顺序闭环：

1. 抓取精确报错：主线程先用全仓或定向 `typecheck` 提取目标文件的当前错误，记录文件、行号、错误码和错误摘要。
2. 下发修复线程：修复线程只处理指定文件或指定切片，交付时必须说明改动文件、修复思路、验证命令和剩余阻塞。
3. 主线程复核：主线程不只看回复，必须实读本轮改动文件，并至少跑一次目标文件定向 `typecheck` 过滤，确认目标报错是否消失。
4. 独立审查线程审查：审查线程基于真实文件、目标报错和验证输出做完整审查，结论必须是 `PASS` 或 `FAIL`，并列出需要返工的问题。
5. 刷新任务状态：只有 `PASS` 后，主线程才刷新全仓错误快照、更新 `stages/current-repair-backlog.md` 的当前主线与最近闭环，再进入下一目标。
6. 第 4 步的 `PASS` 仅代表“当前目标文件/切片通过独立审查”，不代表整个项目已经完成；只要全仓 `typecheck` 未清零，主线程就必须继续刷新热点并进入下一轮，不能用阶段性 `PASS` 冒充整体收口。
7. 第 5 步完成后，如果下一热点已清晰且无外部硬阻塞，主线程必须在同一轮继续推进到“抓取下一热点并派发修复线程”或“至少派发下一线程并进入等待”；不得停在“刚更新完 backlog，还没派下一轮”的中间态。

若第 4 步为 `FAIL`，不得进入第 5 步的“完成”口径；主线程应把审查问题收窄后回派修复线程返工，再重新执行第 3 步和第 4 步。

## 5. 主线程责任

1. 主线程优先负责纠偏与约束审查线程，而非直接替代其全部工作。
2. 只有用户明确要求主线程亲审，才可跳过专用审查线程机制。
3. 每轮审查线程结束后，主线程必须同步更新 backlog 文档和当前主线停点，再进入下一轮。
4. 如果回合被迫中断，主线程下一轮必须先按恢复清单重建“当前在哪一阶段”，再继续返工或进入下一轮；不得默认“审查通过后自然应该开始下一轮”而跳过核验。
