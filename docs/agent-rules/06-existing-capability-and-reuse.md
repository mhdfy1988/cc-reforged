# 已有能力与成熟方案复用规则

用途：防止在仓库已有能力、成熟参考实现或第三方标准方案存在时，重复造轮子、写出第二套业务逻辑或凭印象试错。

## 1. 写代码前必须先确认已有能力

新增、改造或修复功能前，先做最小检索：

1. 查当前仓库是否已有同类 service、hook、component、type、schema、adapter、handler、script 或文档。
2. 查 `src/core` 是否已有统一能力接口；如果没有，优先补 Core API，再让入口层调用 Core。
3. 查 CLI / TUI / SDK / Bridge / Remote / MCP 旧链路是否已经有成熟实现，避免把旧能力误判为不存在。
4. 查 `docs/architecture`、`docs/stages`、`docs/agent-rules` 是否已有设计边界，避免新实现和既有设计冲突。

## 2. 已有能力的处理原则

如果已有能力存在：

1. 优先复用已有实现，不复制一套相似逻辑。
2. 如果已有实现绑定旧入口，优先抽出适配层或收敛到 Core。
3. 如果已有实现类型不适配，优先补类型桥接、schema 或 adapter，而不是新建平行状态机。
4. 如果已有实现暂时不稳定，先记录缺口和复用障碍，再决定是否做阶段性替代。

禁止行为：

1. 已有权限、认证、模型、MCP、工具执行、配置、session 能力时，在 App Server / Desktop / VS Code 中另写一套业务逻辑。
2. 没检索就新增同名或近似 service。
3. 为了快速跑通而绕过现有安全、权限、配置或状态持久化链路。

## 3. 第三方成熟方案优先评估

以下属于通用工程能力，默认先评估成熟库、官方 SDK 或事实标准方案：

1. OAuth / token 刷新 / PKCE / 浏览器回调。
2. LLM provider SDK、流式协议、错误重试、限流处理。
3. MCP client / server / transport。
4. JSON-RPC、HTTP server、WebSocket、IPC。
5. 配置解析、schema 校验、运行时不可信输入校验。
6. 日志、追踪、metrics、测试框架、构建发布工具。
7. 浏览器自动化、文件监听、压缩、路径匹配、diff、semver。

复用前要说明：

1. 它解决什么具体问题。
2. 替代哪些手写代码。
3. 依赖成本和维护风险是什么。
4. 如何通过 adapter 隔离，不污染 Core 领域模型。

## 4. 允许新写实现的准入条件

只有满足至少一项时，才允许新写实现：

1. 仓库没有已有能力，且没有成熟第三方方案适合当前边界。
2. 第三方方案过重、不可控或许可证不适合。
3. 当前阶段是最小原型，但必须记录后续替换计划。
4. 当前是核心领域逻辑，例如 CCR Core 状态机、Agent turn/session 协议、权限语义、工具执行编排。
5. 现有实现已确认不可复用，并已写清楚不可复用原因。

## 5. CCR 当前重点提醒

当前仓库尤其要注意：

1. 权限体系原代码已存在，P8 不能重写权限大脑，只能把已有权限判断和确认流程适配进 Core/App Server。
2. App Server 只是协议层，不得直接复制 TUI/CLI 的业务逻辑。
3. Desktop / VS Code / Web 后续都必须通过同一套 Core API，不得每个入口各写一套权限、模型或工具执行。
4. Codex OAuth 已有本仓实现和外部参考实现，后续改 provider 前必须先对照已有实现与官方/成熟案例。
5. 浏览器 MCP、Playwright、MCP 配置等能力要优先参考成熟实现和现有 MCP 标准，不要凭空手写协议。

## 6. 每次实现前的简短检查句式

开始写代码前，主线程或修复线程应先回答：

1. 仓库里已有类似能力吗？
2. Core 里已有统一接口吗？
3. CLI/TUI/SDK/Bridge/Remote 旧链路里有没有可复用实现？
4. 第三方或官方 SDK 有没有成熟方案？
5. 如果仍要新写，为什么不能复用？

只有这五点有结论后，才进入实现。
